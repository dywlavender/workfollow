# 页面切换实测与修改（2026-10-07）

分支：`experiment/macos-native`。

## 判断

此前 RootShellView 根据目的地切换条件分支，离开模块会销毁页面的视图树，返回时重新创建控件和布局；数据 store 本身是长期存活的，并非每次重新加载全部数据。因此，“每次临时创建页面”确实是成本之一，但不能把全部延迟都归因于它。

日历还有独立的重复计算：CalendarMonthGridView 的初始化参数会提前生成 61 周日期与任务缓存，即使 SwiftUI 已保留原来的 State，重新构造视图值时仍会执行这些计算。

## 修改

- 首次访问时创建 NSHostingView，后续返回复用页面和控件。只有当前页面挂在窗口中，其他页面从布局和焦点链移除。
- 导航栏与侧栏由外层统一管理；缓存任务页和笔记页使用局部导航，隐藏页面不会跟着全局目的地改变而切换内部视图。
- 日历计算移入惰性创建的 StateObject，并在任务或显示偏好变化时更新。
- 避免导航时对已经为空的过滤条件重复赋值、发布无效更新。
- 任务列表的原生容器保持稳定；每个任务范围拥有自己的缓存页面。

缓存会保留已访问页面的内存；第一次创建的成本仍然存在。缓存键限于内置目的地，笔记与笔记垃圾桶共用页面。

## 测量方法

本机 arm64 Debug 构建，使用实际数据（43 条任务），测试窗口 1280×800。按收集箱、笔记、日历、四象限、倒数纪念日、摘要、会议纪要、专注、今天的顺序切换三轮。

每次记录导航赋值、同步布局，以及主 run loop 运行至少 5ms 后再次布局的总时间。这是 CPU 侧导航与布局探针，**不是鼠标点击到屏幕显示完整帧的延迟，也不是刷新率测量**。修改后运行了两次；下表保留两次返回样本的范围，避免只取最好的一次。样本数量有限。

## 验证

构建成功，60 项不同的相关测试通过：先运行 58 项回归，再增加两项并重跑完整的 5 项导航测试。覆盖页面复用、出现/离开回调、隐藏期间任务变更、页面内跳转、列表编辑器复用、日历投影和行布局。
