# 会议纪要第一版：Pi 接入

> 本文记录历史 v1。新录音不再保存为文件，文件路径输入/补转写入口已停用。当前协议与限制见 [内存音频方案](meeting-memory-audio-2026-10-06.md)。下面的 AAC 录音和实机试录结果不适用于新版本。

## 已实现范围

- 侧栏「会议纪要」独立工作区，会议标题、对话记录、滚动纪要。
- 麦克风录音本地保存为约 15 秒的 AAC 分段；暂停时保存最后一段，可以继续录音。
- 会议数据独立保存，不触发 Task workspace 的高频 mutation 链路。
- 所有 AI 请求通过本机 Pi RPC；Native 不访问模型 HTTP API，不保存 API 密钥。
- 有新增对话时约每 25 秒更新同一份纪要，仅传已有纪要和未处理的文字。结束录音只处理剩余内容，不全量重新生成。
- 转写/纪要分别串行；请求失败保留录音、文字和旧纪要，显式重试。手动记录明确标注，不伪装成转写。
- 第一版纪要只读，可复制；避免自动生成覆盖人工修改。

## 接入设置

Pi 路径默认 `/opt/homebrew/bin/pi`。模型填写 Pi 支持的 `provider/model` 标识，留空沿用 Pi 当前模型。认证在 Pi 中完成。

**文字模型可以整理纪要，但无法听音频。仅更换成音频模型也不足以让 Pi 的 Text/Image 消息自动支持音频。** 音频入口使用显式配置的 Pi 扩展，后续仅替换扩展中的模型适配，不改会议存储、录音或界面。

未配置音频扩展：只本地录音，自动转写禁用。已保存音频可以稍后补转写。当前不附带特定厂商音频适配器，不承诺开箱即用的语音识别。

## Pi 音频扩展协议 v1

扩展通过 `pi.registerCommand("wf-meeting-audio", ...)` 注册命令。Native 以 `--no-extensions --extension <绝对路径>` 显式加载它，使用 RPC prompt 调用：

```text
/wf-meeting-audio {"version":1,"file":"/absolute/path/chunk.m4a","offset":15,"knownSpeakers":["A","B"]}
```

扩展负责读取本地音频，通过其配置的音频模型生成结果。完成后使用 `ctx.ui.notify` 返回唯一通知：

```typescript
ctx.ui.notify('WF_MEETING_RESULT ' + JSON.stringify({
  version: 1,
  segments: [{ speaker: 'A', text: '确认下周提交方案。', start: 0.8 }]
}), 'info');
```

- `start` 是**当前音频分段内的秒偏移**，Native 自动加上 `offset`。
- `segments: []` 表示经过模型确认没有可转写语音，不是失败占位。
- 没有可靠说话人信息时省略 `speaker`，显示「未区分」，不虚构身份。
- 跨分段 A/B 身份一致性由扩展负责；`knownSpeakers` 只是提示，不具备声纹匹配能力。选型需验证 diarization 和跨段身份维护。
- 抛出扩展异常会显示接入失败。不要返回伪造文字，或吞掉鉴权/网络错误后返回空结果。
- 音频实际发送到扩展所配置的模型服务，而不是 Pi 自己进行识别。

## 限制与验收边界

这是**分段录音/分段转写**第一版，不是真正连续的 realtime 音频流。转写延迟包括 15 秒分段及模型请求；分段重启存在短暂间隙。需要无间隙实时输入时后续替换录音输送层，不更改会议业务模型。

单元测试验证增量纪要、运行中补入新文字、切换会议隔离、错误保留与重试、持久化、音频协议。测试用 AI 只用于断言调度，不能作为真实音频/模型验收证据。

完整验收仍需配置实际音频扩展和模型，并用两名讲话人的真实录音验证：麦克风授权、分段边界、稳定 A/B 标签、纠正决议、暂停/继续、失败补转写。
