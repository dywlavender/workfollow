# 任务右键误弹侧栏菜单：故障与排查复盘

日期：2026-10-23。分支：`experiment/macos-native`。修复安装版本：`0.2.0 (5)`。

## 结论与影响

用户在任务行右键时，出现“显示 / 隐藏 / 有内容时显示”，无法进入期望的任务操作菜单。这三个选项来自侧栏智能清单的显示设置。共享右键路由错误地把侧栏行的命中范围扩展到了整个窗口，并提前消费了任务区域的右键事件。

本次排查的主要失误是：在用户反复反馈问题仍然存在后，仍围绕版本、主菜单内容和样式继续调整，没有及时验证“到底是哪个控件收到了右键”。此前的安装和隔离组件测试都是真实检查，但它们不足以证明这个用户问题已解决。应由实现与验证过程承担这次漏测，不能归因于用户没有操作新版。

## 已确认的技术原因

1. `NavigationColumnView` 给智能清单行注册 `businessContextMenu`，内容是 `visibilityMenu`。截图中的三个选项可直接对应到该函数及 `SmartListVisibility`。
2. `PopupInteractionRegistry.showContextMenu` 原来直接用 `view.visibleRect` 判断点击是否属于该控件。**在本机未裁剪视图中，`visibleRect` 可以超出控件自身的 `bounds`**；实际测到侧栏行的可见范围覆盖整个宿主窗口。
3. 共享局部事件监听器先于普通视图派发运行。它误判侧栏命中、打开侧栏菜单后返回 `nil`，任务行的 `SecondaryClickCapture` 因而收不到右键。
4. 原来用 `visibleRect` 面积挑选最小目标，也无法可靠区分这些范围同为整个窗口的侧栏行。修复同时约束命中范围与面积比较，二者均使用 `view.bounds.intersection(view.visibleRect)`。

涉及的生产代码：

- 菜单来源：`macos-native/WorkFollow/Features/Sidebar/SidebarViews.swift` 的 `visibilityMenu`。
- 错误判断与修复：`macos-native/WorkFollow/Infrastructure/Presentation/PopupEscapeRouter.swift` 的 `showContextMenu`。
- 被拦截的任务入口：`macos-native/WorkFollow/Features/Tasks/TaskList/SecondaryClickCapture.swift`。

### 可以复核的失败证据

在包含侧栏和任务区的真实 `RootShellView` 隔离窗口中，旧实现出现以下结果。坐标均取自该用例，不是对用户截图像素的估算：

```text
侧栏行 bounds:             (0, 0, 196, 38)
侧栏行 visibleRect:        (-70, -12, 1200, 800)
visibleRect 转成窗口坐标:  (0, 0, 1200, 800)
任务行窗口坐标:            (286, 642, 336, 50)
右键点击窗口坐标:          (454, 667)
错误结果:                  操作菜单
期望的任务菜单 Session:    nil，用例失败
```

该点击位于任务行内，也被所有已注册智能清单行的原有命中判断接收。这个失败结果将“菜单内容不符”定位到了事件路由，而不是菜单绘制或打包环节。

## 为什么之前排查很久

| 排查偏差 | 当时的证据能证明什么 | 缺失的判断 |
| --- | --- | --- |
| 优先怀疑安装包或旧进程 | 版本、路径、新进程及包内容能证明新版已加载 | 新版自身仍可能存在同一个路由缺陷 |
| 持续调整白色卡片的动作与样式 | 能证明目标任务菜单本身更符合参考图 | 用户实际打开的可能是另一个业务菜单 |
| 把独立列表测试视作完整入口验证 | `TaskListView → NativeTaskOutline → TaskRowView` 可以正常打开任务菜单 | 未包含同窗侧栏，因此没有注册会抢占事件的那组目标 |
| 用测试数量代替对症覆盖 | 相关组件、子菜单和数据动作各自通过 | 用例是否保留了触发投诉的窗口结构，比数量更关键 |
| 缺少解决同一症状的失败用例 | 直接创建菜单、调用呈现器能验证下游组件 | 无法证明实际鼠标事件经过上游监听后仍会到达该组件 |

此前修复过的主卡高度、样式和子菜单问题有各自的验证证据，但不能据此推断此次误弹侧栏菜单的问题也已解决。后来的截图给出了明确菜单文案；这类证据应立即用于查找来源，而不是继续沿用之前的样式假设。

## 后续采用的排查步骤

1. **先识别实际打开的东西。** 记录期望菜单和实际菜单的具体文字，搜索实际文字对应的生成位置，确认来源控件、菜单标题与所属窗口。不要只记录“没更新”“样式不对”。
2. **再检查事件归属。** 从鼠标事件到最终处理者追踪，重点查看共享监听器、覆盖层和嵌入的原生视图。必要时临时记录事件位置、目标 `bounds`、可见范围、坐标转换结果及是否消费事件。
3. **保留导致冲突的最小完整窗口。** 本例需要侧栏和任务区同时存在。定位交互问题时，不能为了简化测试而移除可能竞争事件的相邻区域；也不因此扩大到全项目回归。
4. **先让原实现出现同一失败，再改代码。** 本例旧实现应打开“操作菜单”且没有任务菜单 Session；修复后应进入任务菜单。这样才能把修改与用户症状建立因果联系。
5. **只回归实际受影响的路径。** 本例覆盖任务右键、清单切换后的任务右键、侧栏自身菜单、空白区域及嵌套目标优先级；既有子菜单入口与共享业务菜单做关联回归即可。
6. **安装结果与交互结果分别报告。** 包校验、版本、新进程、数据保留用于证明更新成功；完整窗口的事件用例用于证明路由修复。只有实际检查过的日用交互，才能报告为日用窗口已验收。

用户反馈同一症状仍存在时，应将原来的解决假设视为未获支持，补充能区分原因的证据。不要以再次安装或继续美化菜单，替代这个判断步骤。
