# 图标栏对齐滴答清单：栏宽 52→62pt、图标 18→23（2026-10-03）

## 一句话

用户指出「滴答的第一栏更加宽，图标也更加大」。按滴答的实测值把
`RailMetrics` 的栏宽 52→**62**、图标字号 18→**23**（墨迹 16.5→**21pt**），
并让项间距落到 48pt。改后栏宽、图标墨迹、pitch 三项都与滴答一致。

## 读数从哪来（两个独立来源互证）

**① 滴答自己的 AX 树**（它当时在跑，pid 1241，只读）：

```
AXWindow        @0,33 1512x859
AXScrollArea    @0,123 62x601     ← 图标栏，宽 62
  AXRow 62x48  @0,123 / 171 / 219 / 267 / 315 / 363 / 411   ← 行距 48，连续排布
    AXImage 32x32 @15,131 ...     ← 32 是图标**框**，左边距 15 = (62−32)/2，居中
AXButton 34x34 @14,74             ← 头像按钮
AXImage  14x14 @38,70             ← 皇冠角标
```

**② 用户给的滴答截图**（2×）：栏 `x 0..121` = 122px = **61pt**，加 1pt 分隔条 = 62 ✓
与 AX 互证。同一张图量到日历/四宫格墨迹 **42px = 21pt**、行距 **96px = 48pt**。

⚠️ **别拿 32pt 当图标大小。** 那是滴答 `AXImage` 的容器框，不是画出来的尺寸；
真正要对的「看起来多大」只能从截图量墨迹——滴答是 21pt。

## 对照表（同一把尺子：2× 截图，非白阈值 20）

| | 栏宽 | 图标墨迹（日历/四宫格） | 选中背景 | 项间距 |
| --- | --- | --- | --- | --- |
| 改前 · 我们 | 52pt | 16.5pt | 30pt | 46pt |
| **改后 · 我们** | **62pt** | **21pt** | 34pt | **48pt** |
| 滴答清单 | 61pt(+1pt 分隔条) | 21pt | 21pt（= 图标自身填充，无独立背景层） | 48pt |

滴答的选中态是**把图标本身画成填充蓝方块**，外面没有单独一层背景
（截图实测：蓝块 `x 42..82`，`x=40` 与 `x=84` 就已经是背景色 245）。
我们的设计语言是「浅色圆角背景 + 图标」，**这一层保留**，只按比例放大。

## 改了什么

`macos-native/WorkFollow/DesignSystem/Metrics.swift` 的 `RailMetrics`：

| 常量 | 改前 | 改后 | 依据 |
| --- | --- | --- | --- |
| `width` | 52 | **62** | 滴答 AX `AXScrollArea 62x601` + 截图 61+1 |
| `iconSize` | 18 | **23** | 18 × 21/16.5 ≈ 23（用我们自己的实测墨迹比例换算，不是照抄滴答的 pt） |
| `hitSize` | 34 | **38** | 与 `selectedSize` 保持原来的 4pt 差 |
| `selectedSize` | 30 | **34** | 图标 23 时留白 (34−23)/2 = 5.5pt，与改前的 (30−18)/2 = 6pt 基本一致 |
| `selectedRadius` | 9 | **10** | 9 × 34/30 ≈ 10 |
| `itemGap` | 12 | **10** | 38 + 10 = **48**，对齐滴答行距 |

`macos-native/WorkFollowTests/MainWindowChromeContractTests.swift` 里
`XCTAssertEqual(RailMetrics.width, 52)` → **62**（见下面「一个要单独说的事」）。

## 连带效应（这次先查了所有使用点）

改常量前先把 `RailMetrics` / `railWidth` 的每一处出现都列出来，逐个问「这里它是什么语义」：

| 使用点 | 语义 | 是否要动 |
| --- | --- | --- |
| `WFMetrics.railWidth` | 就是栏宽 | 自动跟随 |
| `WFMetrics.navigationBreakpoint` | `railWidth + nav(196) + splitMinimum(621) + 2` | **871 → 881**（导航栏在 881pt 才出现） |
| `MainWindowChromeGeometry.trafficLightFrames` | 按栏宽给红绿灯居中 | 自动跟随，**不用改** |
| `SidebarViews.swift` 的 7 处 | 栏宽/图标/命中框/选中背景 | 自动跟随 |

红绿灯的算法是 `gap = max(0, min(6, (railWidth − 6 − total) / 2))`，`total` = 三个按钮宽 ≈ 42：

- 改前：`min(6, (52−6−42)/2) = 2` → 间距 2pt
- 改后：`min(6, (62−6−42)/2) = 6`（上限生效）→ 间距 6pt

实测：红绿灯从 14pt 变成 15pt（系统绘制，非我们控制）、三个按钮 `x 7..36 / 47..76 / 87..116`
在 62pt 栏内居中。与滴答的 `x 13..42 / 49..78 / 85..114` 相比间距略大 2pt、边距略小 1.5pt
——**没有为这 2pt 再改公式**，因为它落在「够用且不出界」的范围内。

## 这一轮没做的

- **没改图标字形**。我们继续用 SF Symbols，只对齐了尺寸；滴答用的是它自带的图标集
  （实心、更粗），字形层面无法一致。
- **没动选中态的形态**。滴答是「图标自身填充成蓝方块」，我们是「浅色圆角背景 + 图标」，
  保留了自己的语言。
- **没动 `topPadding`（16pt）与竖向起点**。滴答的图标行从窗口顶下 90pt 开始（因为上面有头像），
  我们没有头像，起点本来就不同，用户这次也只说了「宽」和「大」。
