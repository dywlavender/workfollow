# Native 任务取色方案（COLOR-001 … COLOR-006）

日期：2026-10-03。适用：日历月/周网格的任务条、侧栏清单圆点、四象限清单行、专注面板
的清单圆点，以及「选择清单颜色」14 色板入口。

**为什么单独立一份文档**：颜色在这里不是装饰，是**状态载体**——「已完成」靠浓度表达、
「属于哪个清单」靠色相表达、清单身份靠侧栏圆点表达。三条语义共用一张色板，任何一条改
动都会污染另外两条（本方案两次翻车的经过见 [`calendar-task-bar-2026-10-03.md`](calendar-task-bar-2026-10-03.md)
第六、七节）。所以取色规则必须以合同形式钉住，而不是散在 metrics 常量里靠注释提醒。

事实源（唯一）：

### 0…10 的「提艳」修订（2026-10-06）

上表 `0…10` 十一个彩色槽于 2026-10-06 整体重取过色，`11…13` 未动。
起因是用户反馈日历页的任务条「不够亮」。

**根因不在色板，在画法。** 日历条是 `基色.opacity(0.36)` 叠在近白格底上
（格底实测 `rgb(242,244,248)`），**六成四是底色**，任何颜色都被稀释成粉彩——
所以「改基色」对屏幕像素只有 36% 的权重，直接换更亮的基色几乎看不出变化。

**白底上「更浅（L↑）」与「更艳（彩度↑）」是反向的。** 想更艳只能更深，想更浅只能更灰。
本契约 §COLOR-005 记的那次失败正是这条路：把两档 alpha 降到 0.22/0.09 后
L 从 208 升到 218、彩度却从 43 掉到 32，用户仍说「太暗了」——
**这反过来证明用户说的「暗」= 不鲜艳，不是亮度低。**

所以这一轮选的是**不动 alpha、只抬基色饱和度**：HSL 里 S×1.55、L 不变。
真机实测（`screencapture` → 转 sRGB 后采样，2× 图）：

| 元素 | 提艳前 | 提艳后 | 彩度 | L |
| --- | --- | --- | --- | --- |
| 红条 | (238,191,198) | (249,183,190) | 47 → 66 | 200 → 196 |
| 紫条 | (226,184,215) | (238,176,219) | 42 → 62 | 195 → 190 |
| 青条 | (177,214,224) | (176,222,238) | 47 → 62 | 205 → 206 |
| 薄荷条 | (188,224,220) | (187,235,229) | 36 → 48 | 216 → 218 |
| 空白格底 | (242,244,248) | (242,244,248) | 6 → 6 | 244 → 244 |

即**彩度 +30%~45%、亮度基本不动**——这是四个候选（只加浓 α / 提艳 / 提艳+微浓 / 强浓）
里唯一「更艳但不变深」的一档。

**连带影响，改色板前必须知道：**

1. **Flutter 侧必须同步**：`desktop/lib/models/list_color.dart` 的 `listColorPalette`
   是同值同序的表。只改一边，同一条清单在两端会显示成两种颜色。
2. **受影响的不止日历条**：侧栏清单圆点、四象限清单行、专注面板圆点、
   14 色选择器色块，全部走这张表——它们会一起变艳。这是预期的，不是副作用。
3. **旧导出文件里的老 hex 会拿不到下标**：`MigrationSnapshot.taskListMeta(from:)` 用
   `WFListPalette.argb.firstIndex(of:)` 把 hex 换回下标，认不出来时**原样保留 `colorARGB`**。
   所以 2026-10-06 之前导出的 v3 文件再导入，清单会保留当时那个颜色（不丢色），
   只是拿不到槽位下标、不再跟随后续色板变化。这是刻意的取舍，不是 bug。
4. **两个测试钉着首色做金丝雀**：`PlanningViewLogicTests.testPaletteMatchesTheFlutterTokenTable`
   与 `ListMetaTests.testPaletteHasStableFourteenColorsWithDeterministicFallback`；
   迁移测试的夹具里也硬编码了槽 7 的 hex（`MigrationSnapshotTests.swift:69/216`）。
   改色值必须同时改这四处。

**验收留档**（COLOR-006：颜色是屏幕问题，判据是像素）：

| `screenshots/calendar-color-2026-10-06/01-before-original-palette.png` | 改前真机截图 |
| `screenshots/calendar-color-2026-10-06/02-after-resaturated-palette.png` | 改后真机截图 |

| `screenshots/calendar-color-2026-10-06/05-sidebar-dots-after.png` | 连带影响：侧栏清单圆点 |

采样口径：`screencapture` 在 P3 屏上写出的是 **Display P3** PNG，**必须先转 sRGB 再读像素**，
否则原始值与 sRGB 声明值差 7~20/255，会被误判成「颜色不对」。转完与解析模型
（`基色 × α + 格底 × (1−α)`）吻合到 ±2/255。

- `0…10` 是**有彩色**，允许自动分配。
- `11…13` 是**无彩色**，**只允许用户显式选中**，自动分配永不落在这里。
- 这三个值在色板表里保留、在 14 色板 UI 里可点，是**刻意的**：它们属于「用户数据色」，
  是用户表达权的一部分。约束只加在「按规则替你选」的那一步。

## COLOR-002：自动取色不得落到无彩色槽位

`WFListPalette.colorIndex(for:explicit:)` 的自动分支：按清单名做稳定字符折叠（`% 14`，
与 Flutter `listColorValueForName` 同款算法），**若结果落在 11/12/13，折回有彩色**
（11→0 红、12→4 绿、13→8 靛，见 `chromaticFallback`）。

理由不是审美，是**歧义**：日历条的「已完成」档就是同一个色的淡版（α0.12，见 COLOR-005），
所以**一条灰的清单条和一个灰掉的任务在屏幕上是同一件事**。

参照图实测（2026-10-03 复测，`clipboard-2026-10-03T13-40-29-892Z-b69c1862.png`，
3020×1718 的 2× 图）：共 **97 条条带，其中强档 22 条**。强档反推基色后**最低彩度 25**
（橄榄 `(180,188,119)`），其余为青 `(13,133,174)`、橙 `(233,172,99)`、蓝 `(74,147,222)`、
绿 `(36,172,111)`——**没有一条灰的**。

> **测量方法与两个坑（复现用）**：网格是列宽 414px / 行高 310px，条从格顶下 56px 起、
> 步进 38px、高 34px。取样点取 `x = 列左缘 + 395`（条右端内侧）、`y = 条中心 − 13`
> （条上沿内侧）。两个坑：① **不能取条中心那一行**——条右端有时刻文字（`18:00`），
> 会把文字像素当成「低彩度强档」，我一度因此得出「强档里有 17 条灰的」的假结论；
> ② **灰格底 `(242,244,248)` 的容差不能放到 ±5**，淡档填充 `(246,247,239)` 会落进去
> 被当成背景吞掉（实测因此少数 19 条）。
>
> 另外 75 条淡档里只有 21 条是实心框（已完成），其余含**跨天色带**（无勾选框）与
> **非本月格**里更淡的一档（`(246,248,254)` ≈ α0.05）。所以模型是**单向**成立的：
> **强档 ⇒ 未完成**（22/22 无例外）；**已完成 ⇒ 淡档**（21/21）。反过来不成立。

显式选色不受此约束：`if let explicit, explicit >= 0, explicit < argb.count { return explicit }`
在自动折叠之前返回，用户点 14 色板里的暖灰/板岩/灰，照旧生效。

回归资产：`testAutoColorNeverLandsOnAchromaticSlots`（400 个构造名 + 8 个真实名）。

## COLOR-003：日历条按**任务**取色；侧栏 / 象限 / 专注按**清单**取色

这是一条**有意的分裂**，两套取色并存：

| 界面位置 | 取色依据 | 入口 | 它回答的问题 |
| --- | --- | --- | --- |
| 日历月/周网格的任务条 | **任务** | `WFPlanningPalette.taskColor(taskID:)` → `WFListPalette.taskColorIndex(for:)` | 「这几条是同一件事吗」 |
| 侧栏清单圆点 | 清单 | `WFPlanningPalette.listColor(name:meta:)` | 「这个清单是什么颜色」 |
| 四象限的清单分组行 | 清单 | 同上 | 同上 |
| 专注面板的清单圆点 | 清单 | 同上 | 同上 |

### 为什么分裂

**因为清单色那条路对「收集箱」是堵死的，而 20/35 条任务都在收集箱。**

链路是：`WFListPalette.color(for:meta:)` → `colorIndex(for:explicit:)` →
`TaskActions.setListColor` → **`ListMetaTests:104` 断言 `setListColor` 对收集箱返回 `false`**。
也就是说「清单选色 UI」虽然早就存在（`TaskManagementViews.swift:203` 的 14 色板），
但收集箱这个清单**被明确设计成不可着色**。于是只要按清单取色，日历就永远是一整片同一个蓝。

按任务取色**绕开**这条堵死的路，而不是去改它。

> **方法可迁移**：摸链路时先找「**哪条路被有意堵死**」，比找「缺什么功能」更常命中。
> 这里有断言文件当证据，一眼能确认「不是没做，是不让做」。

### 代价（必须记住，不要当成 bug 报回来）

- **日历条不再告诉你任务属于哪个清单。** 侧栏圆点、象限行、专注面板**没有跟着改**，
  所以同一个任务在日历和侧栏可能不是同一个颜色。这是分裂的既定代价，不是漂移。
- 一天内**偶尔两条同色是正常的**：11 个槽抽 5 次只有 **34%** 的概率全不撞
  （`10·9·8·7 / 11⁴ = 0.344`）。参照图 5 日那格自己也有 3 条同色。**不要为撞色加"避重"逻辑**——
  那会让颜色依赖当天可见任务集合，翻月就换色，比撞色更糟。

### 保留的备选（一行可切）

若哪天更看重「日历与侧栏同色」，可以把 `barColor` 改回按清单、**只对收集箱走按任务**。
这条路保留了清单语义，代价是收集箱内仍然花、清单之间仍然整片同色。当前选择的是**全按任务**。

## COLOR-004：取色必须是纯函数，禁用 `String.hashValue`

任务取色用**手写 FNV-1a 64 位**：

```swift
var hash: UInt64 = 0xcbf2_9ce4_8422_2325              // 偏移基数
for byte in taskID.uuidString.utf8 {
    hash = (hash ^ UInt64(byte)) &* 0x0000_0100_0000_01b3   // 质数
}
return Int(hash % UInt64(chromaticSlotCount))         // % 11
```

**不能用 `String.hashValue` / `UUID.hashValue`**：Swift 的字符串散列**每次进程启动换种子**，
用它定色，日历每次重开都会换一套颜色——用户会看到任务在"变色"。这不是抖动，是**记忆失效**。

实测：35 个真实任务 id 铺满全部 11 个有彩色槽位；测试里 160 个构造 id 每槽 12~18 条。
`chromaticSlotCount` 由 `private` 改为 internal，就是为了让测试能把它当上界引用
（`testTaskColorIndexIsDeterministicChromaticAndSpread`）。

## COLOR-005：条底两档浓度 = 完成 / 未完成，取参照物原值 0.36 / 0.12

**这两档不是「强调 / 次要」，就是「未完成 / 已完成」本身。**

| 状态 | 常量 | 值 | 标题墨色 | 勾选框 |
| --- | --- | --- | --- | --- |
| 未完成 | `taskBarFillAlpha` | **0.36** | 深墨 | 空心描边 |
| 已完成 | `taskBarCompletedFillAlpha` | **0.12** | 浅灰 | 实心灰底 + 白勾 |

同一个色相画在两个透明度上，**离白距离正好 1:3**。参照图三条独立证据：

① **同色相两档的三通道比值一致**：蓝 0.34/0.33/0.33、橙 0.38/0.33/0.34、绿 0.33/0.32/0.34。

② **强档与完成态不重叠（逐条验证，无例外）**：全图 97 条条带、22 条强档，这 22 条的
勾选框区域**灰像素占比全部为 0**（即全部是空心框 = 未完成），**「强档 + 实心框」= 0 条**；
反向，21 条实心框（已完成）**全部落在淡档**。分类是干净的：灰占比在 0.1~0.35 之间
**一条都没有**，不存在边界样本。
（此前文档里写的「59 条交叉表 / 56 实心 / 3 空心」是错的，已按本节复测替换。）

③ **网格线与格底逐像素相同**：两档是真实状态，不是整片被压暗或合成出来的。

### 铁律：「调淡」≠「提亮」——降 alpha 会同时降**彩度**

这是本方案付过学费的一条。曾为「一格堆 5 条同色强档太压人」把两档降到 0.22 / 0.09，
用户随即反馈「**颜色太暗了**」。实测：

| | 亮度 L | 彩度 `max−min` |
| --- | --- | --- |
| 滴答 蓝 | 212.4 | **53** |
| 滴答 绿 | 214.0 | 49 |
| 滴答 青 | 202.9 | 58 |
| 我们 α0.32 | 208.1 | 43 |
| 我们 α0.22（错的那一刀） | 217.9 | **32** |

亮度确实上去了（208→218），**彩度掉了四分之一**（43→32）。「浅」变成了「灰」。
滴答的条是**浅而艳**，那一刀做出来的是**浅而灰**。

**规则：**
1. 用户说「暗」时，**同时量亮度和彩度**。「暗」在中文里常常指「闷 / 不鲜艳」，不是亮度低。
2. 判断参照物是不是「浅而艳」，算 `max−min`（彩度），别只看 L。
3. **同色堆叠不该用降浓度去解，该用改取色去解**（COLOR-003）。浓度是旋钮，但它调的是
   「一条的轻重」，不是「一格的轻重」。

### 两档 alpha 是旋钮，但下界是硬的

`PlanningMetrics.swift` 里各一行。**再往下调要先确认已完成档还看得见**——实测 0.075 时
