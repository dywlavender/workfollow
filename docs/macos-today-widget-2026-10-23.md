# macOS「今日待办」桌面小组件

日期：2026-10-23。分支：`experiment/macos-native`。

## 本轮范围

实现原生 WidgetKit 扩展，首版提供中号「今日待办」卡片。用户已确认暂时没有 Apple 开发者账号，本轮完成源码与隔离验证，不安装或替换日用版，不将真实任务导入测试组件。

- 今日安排和逾期任务：最多显示四条；逾期优先，同组按优先级和安排时间排序。父任务已在卡片中时不重复展示其子任务。
- 显示今天已完成数量、逾期数量、超出卡片容量时的待办总数，以及本周剩余任务。今天已完成数按完成日期统计，不累计历史完成任务。
- 勾选完成走主应用既有任务动作；重复推进、撤销、持久化及 Apple 提醒事项联动沿用已有业务链。
- 点标题打开任务详情；点加号打开日历同款的快速新增卡；点本周剩余任务进入当前自然周的周计划。
- 未建立共享快照时引导打开应用；无待办时显示空状态。支持浅色、深色，以及主应用退出后的预置跨日展示。
- 本周剩余数量沿用周计划的自然周与显式周归属规则，包含已安排进本周但尚未确定具体日期的任务。

## 数据与完成操作

`WidgetShared` 同时编入主应用与小组件扩展，只包含任务元数据、组件视图和通信协议；不复制任务正文或提供可写的工作区数据库。

主应用将活动清单中的可用任务投影为精简快照，采用原子文件写入。归档清单、删除、跳过、放弃和已转为笔记的任务不进入组件。普通任务变更合并后请求 WidgetKit 刷新，时间线提前准备未来七天的日期切换；系统最终调度刷新，不承诺外部改动的固定秒级刷新时间。

组件的完成 App Intent 将独立请求写入共享目录，通知并尝试在后台唤醒包含它的主应用，不主动激活主窗口。主应用校验任务版本，调用既有 `TaskWorkspaceModel.complete`，等待工作区保存完成后返回结果并更新快照。重复请求只确认已完成的原任务，不会改为完成下一条重复实例。任务已修改时更新组件并要求重新勾选。

现有 `workfollow://task/<任务ID>` 链接继续使用。新增导航入口：

| 链接 | 行为 |
| --- | --- |
| `workfollow://widget/today` | 打开今天，清除旧筛选和详情选择 |
| `workfollow://widget/add` | 独立打开快速新增卡，默认今天，保留主页面与当前任务选择 |
| `workfollow://widget/week` | 打开当前自然周，清除旧清单筛选 |

## 组件快速新增（2026-10-24）

组件加号复用日历的 `TaskQuickComposer`，使用 320 × 212 的轻量浮窗，靠近点击位置并限制在屏幕可见范围。打开后直接输入标题，可调整日期、优先级、清单、提醒和重复；回车创建后收起，Esc 或点击外部取消。重复点击加号保留同一张卡片和未提交草稿。

默认创建今天的全天任务，清单为收集箱；不继承主页面的标签和筛选，不清除详情选择，也不在创建后跳转详情。URL 接收器在应用初始化时接线，快速新增不调用主窗口激活；主场景改用单个 `Window`，避免外部链接产生重复主窗口。

当前导航会保留用户浏览的周，因此组件“本周剩余”入口单独调用 `goCurrent()` 并清除周计划清单条件，确保它仍打开组件所统计的本周全部任务；普通侧栏导航继续保留浏览位置。

11 项相关 XCTest 已通过，覆盖组件新增、草稿保留、回车提交、日期子卡、逐层取消、资源链接和本周入口。属性菜单测试等待原生菜单完成内容测高后再点击选项。未进行全量回归。系统中应用运行及退出两种状态下的组件点击仍需单独验收，不能用进程内路由测试代替。

日用安装包已更新至 `0.2.0 (13)`，主应用与扩展版本一致，均使用已验证的本地组件容器通道。安装前正常退出并备份应用及工作区，替换前后任务、笔记及正文表数量一致。原生工具能读取正式组件，但点击目标在 WorkFollow 与电池组件间错位，未能实际启动宿主；已请用户直接点击组件加号，退出后的窗口呈现尚待确认。

## 工程与打包

- 新增 `WorkFollowWidgets` 扩展目标，嵌入 `WorkFollow.app/Contents/PlugIns/WorkFollowWidgets.appex`。最低系统版本沿用 macOS 14。
- 工程默认使用正式 App Group：`group.com.workfollow.native.widgets`；本地打包脚本为临时签名明确选择组件自身容器。两种通道均保留扩展的 App Sandbox。
- 本地打包脚本允许此指定的 WidgetKit 扩展，继续拒绝测试插件及未知扩展。本机签名按扩展、主应用的顺序签名；本地通道不声明 App Group，正式通道沿用 Xcode 授权的 App Group。
- 使用正式签名时由 Xcode 配置的团队和描述文件完成授权；移除验收配置后的主应用重签保留 Xcode 生成的权限与签名规则。
- 独立 XCTest 宿主不用生产共享组，测试构建关闭正式签名要求，数据留在临时测试目录。
- 通用设置增加添加组件的说明，无新增开关或需要用户填写的配置。

## 本机探针的实测限制与结论修正

当前没有可用的正式代码签名身份。隔离签名探针能解析 App Group 的目录地址，但创建独立验收标记时被 macOS 拒绝写入；当前工程的 App Group 自动签名构建也要求开发者证书。之后又通过 LaunchServices 正常启动有界面的隔离应用，并从按钮发起同一共享组的读写，仍返回 NSCocoaErrorDomain / 513。这证明当前配置下该通道未打通，不能推出所有本地自用小组件都必须购买开发者账号。

Apple 的[沙盒文件访问说明](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)明确区分自动授权条件与需要用户授权的其他情况，不能将一次写入拒绝一概解释为没有开发者证书。此前“必须等开发者签名”的表述过于绝对，现予修正。

## 本地自用路线（已接入，原生任务动作已通过对照）

[tauri-plugin-widgets 作者文档](https://s00d.github.io/tauri-plugin-widgets/guide/setup/macos)提供了原生 WidgetKit 的本地临时签名方案：由未沙盒化的主应用将数据写入小组件自身容器，扩展继续从自己的沙盒容器读取。该项目将此通道称为 `widgetContainer`，与正式 App Group 通道分开配置。

当前 WorkFollow 主应用未启用 App Sandbox，扩展已启用，符合此路线的结构条件。本地打包时向主应用与扩展写入相同的 `WorkFollowWidgetTransport = widgetContainer`；正式构建默认使用 `appGroup`。运行时只使用指定通道，不同时向多个位置写入。

本地通道由扩展在自己的 Application Support 目录读写，主应用使用该扩展对应的容器目录。主应用等待系统先初始化组件容器，不自行创建容器根目录。首次添加组件、激活主应用或收到组件请求时重试生成快照。完成请求、持久化确认和任务版本校验沿用已有协议。

macOS 27.0.1 的隔离实测：

- 正常启动的沙盒测试组件成功创建自身容器并写入标记；未沙盒化的测试主应用成功读取并回写；组件成功读取回写并清理一次性标记。三个步骤均有独立结果记录。
- 使用当前 WidgetShared 视图、完成 Intent 和精简模拟任务宿主构建真正的 WidgetKit 扩展，临时签名后通过严格签名验证。该副本使用独立标识、独立链接协议和四条模拟任务。
- 正常启动隔离副本后，系统小组件库列出「WorkFollow Widget Local QA」，并成功渲染「今日待办 · 隔离验收」的原生预览。证明系统能够识别和运行此临时签名扩展。
- 用户已手动添加到桌面；WidgetCenter 报告 1 个已添加的验收组件，Provider 记录成功读取四条模拟任务。
- 主应用退出后的首次勾选没有改变任务。独立验收标识对应的系统日志确认收到 `CompleteWidgetTaskIntent` 按钮事件，但动作执行器报告找不到主应用的动作元数据；实际包内元数据存在，未生成完成请求，也未改变模拟任务。不能将此解释为完成动作已通过。
- 早期验收更新包放到 `/Applications/WorkFollow Widget Local QA.app`，构建号为 3；此前临时目录中同名包已移除，模拟任务和桌面组件保留。系统随后报告过旧扩展版本与登记版本不匹配，时间线更新被拒绝；这条旧副本路线未能恢复有效动作登记。不能据此认定临时签名无法运行交互动作。
- 上述旧副本当时只通过桌面加载，未通过勾选回写。随后使用固定安装位置、全新标识的对照程序通过了原生任务动作、主应用退出唤醒和持久化重启，详见下方复验记录；不能将两份副本的结果混为一组。

本轮未安装或替换日用版，也未更改系统安全设置。正式签名的 App Group 路线仍可用于以后发布。

## 桌面勾选失败的原因分析（2026-10-23 追加）

用户要求先分析原因，暂不继续修改业务实现或请求重复点击。

针对旧副本的证据将失败定位在系统动作执行入口，尚未进入任务完成代码：

- 更新前的扩展进程确实仍从已移除的临时路径运行，而 PlugInKit 已登记标准应用目录的新路径。其日志报无法将进程映射为应用记录。这是明确的验收副本迁移问题。
- 只结束旧验收扩展与模拟宿主，并从标准路径重启宿主后，桌面点击仍报告 `ChronoCoreErrorDomain / 1: Unknown extension process`。目前只有标准路径的宿主进程，桌面实例未成功关联到可执行的新扩展。重启进程并未恢复这层绑定，不能继续按“已经修复”安排复测。
- 当前新版宿主被 `linkd` 报告 `Failed to generate bundleIdentity / Unable to get teamId`。主应用与扩展均为临时签名，`TeamIdentifier=not set`。这是独立的身份注册报错，可能阻止 App Intents 注册或执行；尚不能据此推出所有本地交互组件都必须购买开发者账号。
- 主应用与扩展的包内均实际包含 `CompleteWidgetTaskIntent` 元数据，所以此前“没有元数据”的系统报错不等于构建遗漏了元数据文件。
- 任务完成请求与回执仍均为零，模拟任务完成数仍为零；之前收到过今天、本周与任务详情的普通链接。因此已有数据读写和普通链接可用，尚无证据表明故障位于任务持久化或共享容器。

本地组件容器解决的是快照与请求文件共享，不能同时证明系统认可 App Intent 的调用身份。8 项 XCTest 与 4 项打包测试也不覆盖真实系统中的动作注册，不能代替桌面勾选验收。

当时的下一步是在固定安装位置用全新验收标识建立一个无参数、无任务依赖的最小动作，只判断系统是否执行 `perform()`。该对照随后已实施并成功，结果见下一节；不需要根据旧副本的失败改为链接完成任务。
