# 对话文字实时性实验

## 原因

当前录音采集等待约 10 秒后才寻找 300ms 安静边界，连续讲话最多约 20 秒后发送。随后 Native 启动 Pi 请求，等待完整模型响应及 JSON 校验后追加文字。纪要的 25 秒心跳不控制对话文字显示。

## 已实验的候选

增加 `.responsive` 分段策略：2 秒后遇 300ms 停顿发送，连续讲话上限 5 秒。共用现有连续 PCM 采集、队列和 Pi 路径，不保存音频。

代码及 helper 保留候选，**正式录音仍使用原策略**。未新增 UI 设置。不能因为采集层通过就升级为默认。

## 模型测试

使用相同的 27.09 秒虚构双声线合成对话，只经 Pi 上传，音频不落盘，未使用麦克风。

- `meeting-speech-responsive-2026-10-06.json`：前两段成功，第三段返回无效 JSON，失败。
- `meeting-speech-responsive-diagnostic-2026-10-06.json`：9 段完成，其中尾段数字静音返回空转写；非静音段请求耗时 978–1149ms。归一化字符错误率约 1.09%。明确把一次“小李”错为“小雨”，并导致纪要负责人被错误更新。整体讲话人检查也未通过，不能以字符错误率较低声称整体成功。
- `meeting-speech-responsive-recheck-2026-10-06.json`：第六段有文字但漏了必需 start 字段，按现有契约拒绝，失败。

完成全程的一次，第一段长度 5 秒、Pi 请求耗时 1.149 秒，采集时长加请求耗时估算为 6.149 秒。这不是实机麦克风到屏幕实测。测试快速顺序发送预生成的 PCM，没有模拟真实时间队列积压。

这三次没有可靠证明失败由短分段引起；此前模型在长分段/常驻实验也有格式失败。请求增多暴露了当前输出契约的稳定性问题。没有通过改校验规则、填补模型字段或只保留成功样本来掩盖失败。

## 代码回归

候选增加两个测试：短停顿 2.3 秒输出；连续讲话每 5 秒切段、尾段及字节完整不丢失。包含既有录音、纪要与 Pi 调用归属回归，共 20 项 Swift 测试通过。

诊断扩展只供虚构合成音验收，记录模型文字，不记录 PCM。正式 App 不加载该扩展。

## 下一步

不继续靠缩短分段追求实时性。下一轮验证 Pi 内增量转写通道：实时草稿与最终转写分开，草稿不进入纪要；最终结果定稿时原位替换而不是重复追加；停止后处理最后一段，切换会议不误写。先核实当前端点的增量输入转写事件，再实现，所有连接仍由 Pi 所有。该路径尚未实现，不能声称已经支持逐字实时显示。
