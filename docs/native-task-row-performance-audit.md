# 原生任务行与刷新范围排查

日期：2026-11-01。分支：`experiment/macos-native`。

## 已确认的开销与修改

清单已有原生 `NSOutlineView`，但此前每条任务仍创建 `NSHostingView`，其内部维护独立 SwiftUI 视图树。首次显示清单时，任务行的初始化、布局和布局桥接占用了主要时间。仅缓存清单投影或复用外层列表，无法消除这一层成本。

现在普通任务行由 `NativeTaskRowView` 显示：原生文本字段、按钮、标签和图层共用固定的行高与缩进规则。标题编辑直接复用原有 `TaskRowTitleField.Field` 和协调器；任务变更继续调用同一 `TaskWorkspaceModel`。分组标题保留 SwiftUI 宿主，日期面板按打开动作创建，均不再给每条任务常驻一个宿主。

| 位置 | 确认的问题 | 本轮处理 |
| --- | --- | --- |
| `TaskListView` / `NativeTaskOutline` | 每条任务维护 SwiftUI 宿主；换清单时创建、布局一批行 | 普通任务改为 AppKit 控件，按任务身份复用；单选直接刷新原生选中背景 |
| `TaskLayoutObservation` | 转发整个任务数据观察器，普通任务内容和折叠变化也通知外层分栏 | 仅观察清单上下文、是否多选、是否打开详情和分栏宽度；已打开详情时 A → B 不通知外层布局 |
| `TaskKanbanView` / `TaskKanbanCardView` | 看板外层订阅完整工作区，单选也重新设置列宿主的 `rootView` | 外层仅观察任务数据；具体任务行继续观察选中状态，保留高亮 |
| `TaskTagManagementView` | 标签侧栏订阅完整工作区，普通任务单选也触发标签树计算 | 改用任务数据观察器，标签目录和标签作用域变化仍会更新 |
| `NativeTaskOutline` 行动效 | 首次加载和跨清单切换仍可能播放整批增删动效，初始化还会重复刷新首屏 | 首次加载和跨清单不播放行增删动效；清单内添加、删除和展开仍保留动效 |
| 滚动后缩短列表 | 回归中复现可见行区间超出新数据范围；短列表仍保留旧滚动偏移 | 可见行区间同时限制在数据和 outline 行数内；内容缩短至一屏时重置滚动位置，避免旧动画几何干扰 |

## 外观和交互

任务行保持现有字号、缩进、背景、优先级颜色、标签、正文预览和日期表现。深浅色固定样例分别导出旧行与新行图片，对照时修正了原生文本字段的对齐偏移和子任务箭头颜色。悬停提示复用现有 `HoverTipTrackingView`，日期面板与右键菜单继续使用现有呈现组件。

验证覆盖完整外壳中的侧栏与任务行，而非只在孤立任务行上判断右键归属。还覆盖单击标题编辑、中文输入法组合文本跨清单提交、日期按钮不选中任务、完成与恢复、批量选择、层级和排序、滚动与短列表切换。

## 其他页面的排查

以下是源码层面的观察，尚不是性能故障结论；本轮没有据此批量改写其他页面。

| 位置 | 观察 | 后续应如何判断 |
| --- | --- | --- |
| `NotesWorkspaceView` | 订阅完整任务工作区，用于分栏宽度和关联任务；这两类状态变化频率不同 | 分别测量调整宽度、任务单选、关联任务变更。若编辑器受无关刷新影响，将宽度和关联任务拆为局部观察，不能直接替换成不观察宽度的数据包装器 |
| `MatrixWorkspaceView` | 外层、棋盘和部分卡片均订阅任务工作区，外层还计算象限投影 | 记录选中任务时象限投影和卡片宿主更新次数；保留需要选中态的行，只收窄无关外层 |
| `CalendarWorkspaceView` | 订阅完整任务工作区；已有按任务版本和日期版本缓存的发生项投影 | 先区分投影缓存命中、日历布局和详情浮层成本，不能仅凭订阅方式判定它同样卡顿 |
| `TaskInspectorShell` | 同时承担当前任务、关联任务、属性面板和编辑状态 | 测量无关任务变更是否更新当前文档编辑器，再考虑局部任务观察。选择变化本身是必要输入 |
| `AIConversationView` | `LazyVStack` 按消息身份渲染，没有给每条消息创建 AppKit/SwiftUI 宿主的桥接结构 | 没有发现本次同类结构；流式长回答的 Markdown 成本需要单独测量 |
| 日期、菜单、编辑浮层 | 按需创建或复用单个 SwiftUI 宿主 | 这类宿主数量不随可见任务行数增长，不属于本次首要问题 |

这轮优化的边界是减少重复构建和无关刷新。SwiftUI 本身、主题背景或使用观察对象，都不能单独作为“架构不合理”的证据。

## 对照方法

使用同一份源码和 60 条虚构任务，在 1280×800 窗口中分别测试普通背景、极光主题，依次切换三个自建清单、今天和收集箱。DEBUG 环境变量 `WORKFOLLOW_REFERENCE_TASK_ROWS=1` 仅在测试中启用旧任务行，便于与新原生行做同条件对照；正式版没有此开关。

记录导航、布局、绘制、创建宿主数和原生行数。性能测试应在编译完成后串行运行，避免并行构建竞争 CPU。首次进入与已缓存后的再次进入分别统计；测量是 Debug 的更新、布局和绘制阶段，不代表所有真实数据和设备的点击延迟。

## 最终结果

同源码串行 A/B 对照，每种背景首次进入自建清单 3 个样本，再次进入 6 个样本。再次进入的样本也包含从已打开详情切回清单的情况。

| 场景 | 旧 SwiftUI 任务行，中位耗时 | 新 AppKit 任务行，中位耗时 |
| --- | ---: | ---: |
| 普通背景，首次进入清单 | 136.96 ms | 85.63 ms |
| 普通背景，再次切换清单 | 46.27 ms | 32.62 ms |
| 极光主题，首次进入清单 | 154.43 ms | 72.42 ms |
| 极光主题，再次切换清单 | 47.31 ms | 33.96 ms |

首次进入自建清单的累计行布局中位耗时，普通背景由 97.04 ms 降至 2.59 ms，极光主题由 107.70 ms 降至 2.60 ms。每种背景的三次首次进入中，旧版合计创建 36 个任务行 SwiftUI 宿主；新版创建 36 个原生任务行、0 个任务行 SwiftUI 宿主。再次切换均复用已有行，没有新建任务行。

智能清单也测量了“今天／收集箱”：再次进入的中位耗时，普通背景由 60.43 ms 降至 32.58 ms，极光主题由 56.08 ms 降至 33.80 ms。普通背景旧行有一个 218.06 ms 的样本，因此同时保留中位数、最大值和全部原始样本，避免用单次最好结果代表稳定表现。

原始数据：[native-task-row-performance-2026-11-01.json](research/native-task-row-performance-2026-11-01.json)。本对照已共用本轮其他刷新优化，比较的变量是任务行实现；不能把这里的全部收益重复归因于看板、标签侧栏等修改。

最终定向回归选中 211 项，210 项通过、1 项因为隔离库没有至少两条真实任务而跳过，0 失败。新旧任务行性能对照另有两次独立测试通过。完整外壳中的看板选择回归确认列身份保留，当前列 `rootView` 重设次数为 0；计数限定在当前窗口，避免混入其他用例窗口的异步更新。
