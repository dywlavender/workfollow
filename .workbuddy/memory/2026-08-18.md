## 页面高度填充问题修复

### 现象
用户反馈：导航到不同页面、特别是内容少的页面（如通知、常用），body 高度"不够覆盖整个页面"，看起来下方有大片空白。

### 根因
- `body`/`html`/`#app`/`.app-shell`/`.main-area`/`.page-content` 都已经正确撑满视口高度（实测 h = vh = 900）。
- 但 page 内的"主区域"（`.notification-list`、`.common-links-body` 等空状态/列表容器）只有自身内容高度（`min-height: 160~280px`），且它们的父容器不是 flex column，所以无法吸收剩余空间，导致视觉上空荡。

### 修复
文件：`frontend/src/layout.css`
在原有 `.page-content` 规则块后新增 11 行：
```css
.notifications-page,
.common-links-page {
  display: flex;
  flex-direction: column;
}
.notifications-page > .notification-list,
.common-links-page > .common-links-body {
  flex: 1 1 auto;
  min-height: 0;
}
```
仅影响这两个页面，其它页面（todos/calendar/notes/settings/teams）布局不变。

### 验证（1440×900 视口）
| 元素 | 修复前 | 修复后 |
| --- | --- | --- |
| `.notification-list`（通知页空状态） | ~160 px | **751 px** |
| `.common-links-body`（常用页主区） | ~280 px | **823 px** |
| `.state-message.empty`（"暂无通知"） | 160 px | 居中在 751 px 卡片内 |

`npm run type-check`、`npm run tokens:check`、`npm test`（33/33）全部通过。

## 团队页宽度契约收敛（与首页不同：内容页限宽是正确设计）

## 大屏通用缩放方案（用户反馈 + 方案演进）

### 演进路径
1. **第一版（被推翻）**：仅放大 rail（60→72、40→48、19→22）。用户反馈"不合理——大屏整个页面都有问题，应该有通用方案"。**用户洞察正确**：只放大 rail 导致内容区不变，比例不协调，是打补丁不是方案。
2. **第二版（zoom 全局缩放）**：试 `.task-app-shell { zoom: 1.1 }` 一行全局。**失败**——zoom 让 100dvh 锁视口容器视觉放大 10%，1920 下 docH=1188 > vh=1080，任务/笔记页底部 108px 被挤出，等于把最初修的高度问题重新引回来。zoom 与 100dvh 锁视口契约**结构性冲突**。
3. **第三版（最终）**：**token 大屏舒适档**——项目字号/间距/rail-width 已是 CSS 变量体系，派生变量全引用基础 token（`--card-title-font-size: var(--type-panel-title-size)` 等），在断点下覆盖基础 token 即可**全树联动**。项目没有 rem 基础，迁移 rem 成本过高，token 覆盖是"零迁移的通用方案"。

### 改动（layout.css 末尾新增 @media (min-width:1600px) 块）
- :root 覆盖：12 个 --font-size-* 整体上移 1~2px（micro 10→11 ... display 32→34）、8 个 --space-* 上移 1~2px、--workspace-rail-width 60→66
- 派生变量（--type-page-title、--card-title、--dialog-*、--input-* 等）全部 `var(--font-size-*)` 引用，**自动跟随基础 token**
- rail 内部硬编码 px 补充覆盖：sidebar padding 8→8（内容区 50）、brand 40→44、brand-mark 32→36、rail-item 40→44、glyph 19→21（CSS 覆盖 svg width/height）、avatar 28→31、user-card 40→44、rail-badge 17→18

### 验证
- **断点行为**：1440/1599 保持小屏档（body 14、rail 60、item 40、glyph 19、brand 40、avatar 28）；1600/1920/2560 切大屏档（body 15、rail 66、item 44、glyph 21、brand 44、avatar 31）
- **100dvh 锁视口保持**：所有档位 `docH === vh` ✓（zoom 方案失败的核心原因被规避）
- **派生变量联动**：--type-page-title-size 22→23、--card-title-font-size 跟随放大
- **全页面回归 @1920**：/、/todos、/notes、/calendar、/common、/notifications、/settings、/teams 全部 `docH=1080=vh`、无溢出、rail 66
- 门禁：type-check ✓ / tokens ✓ / test 33/33 ✓
- 截图：`output/layout-fix/home-1440-token.png` vs `home-2560-token.png`（2560 下整个页面字号/间距/rail 全部协调大一档）

### 关键教训
"通用方案"不一定是一行 zoom 之类的"魔法开关"。在 px + CSS 变量体系下，**token 覆盖是最贴近体系本身的通用杠杆**——零迁移、保留所有契约（100dvh 锁视口、宽度上限、内容页居中等）、派生变量全树联动。zoom 看似更通用，实则与 100dvh 结构性冲突。
